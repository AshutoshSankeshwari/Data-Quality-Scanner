Data Quality Scanner

Deployment Guide — Installation, Configuration, Validation & Operational Setup
Target Environment: Production Standalone
Validated Platform: Windows 10/11 (64-bit)
Runtime: Python 3.11+ (64-bit)
Audience: Deployment Engineers, Data Engineers, IT Administrators

1. Purpose and Scope

This guide defines the authoritative, repeatable engineering procedure for packaging, installing, configuring, validating, maintaining, and supporting Data Quality Scanner on target host machines.

Scope of This Document

  • Covered: Host preparation, Python virtual environment configuration, offline/online dependency resolution, configuration governance, static asset deployment, SQLite persistence lifecycle, desktop GUI launcher setup, headless CLI script automation, formal smoke testing, version update procedures, backup/restore sequences, emergency rollback, and deployment troubleshooting.
  • Not Covered: End-user analytical navigation, interpretation of specific business defects, manual data remediation workflows, or authoring custom ETL migration scripts. For operational end-user procedures, consult the companion Data Quality Scanner User Guide.
📘 Companion Relationship to User Guide

The User Guide is intended for migration specialists, data analysts, and project managers for daily assessment tasks. The Deployment Guide is strictly for technical personnel responsible for ensuring the scanner is securely installed, correctly calibrated, and reliably operating on the host environment.

Architectural Boundary Notice

Data Quality Scanner is implemented and validated exclusively as an isolated, local standalone application. The following architectures are Not applicable to the current DEPLOYMENT GUIDE model:

  • Containerization frameworks (Docker, Kubernetes, Podman).
  • Cloud SaaS, microservices, or distributed multi-tenant deployments.
  • Centralized database clusters or remote relational database servers.
  • Web applications, REST APIs, or background Windows service daemons.
  • Binary installers (.msi or .exe installer packages).

2. Deployment Model

The scanner utilizes a single-node, file-based deployment model. Both available user interfaces—the Desktop GUI (main.py) and the Headless Batch CLI (batch_runner.py)—execute on top of an identical analytical engine within an isolated Python virtual environment (.venv).

Key Architectural Characteristics

Characteristic Implementation Details
Host Architecture Single workstation, laptop, or designated virtual machine running Windows 10/11 (64-bit).
Runtime Isolation Local CPython virtual environment (.venv) created via Python's standard venv module. Isolates all application dependencies from system packages.
Cloud & Server Independence Normal execution does not require a remote application server or cloud service. Where outbound package installation is restricted, dependencies can be supplied through an approved offline/internal package source.
Persistence Layer Embedded SQLite database (data/scanner.db) managed via WAL mode. Auto-initializes on first execution.
Data Confidentiality Source records are loaded strictly into host memory for heuristic evaluation. Raw dataset rows are never persisted to the SQLite database.

6. Environment Setup

Execute the following numbered procedure on the target host using Windows PowerShell (or Command Prompt) to establish the isolated Python environment.

Step 1 — Unpack / Copy the Deployment Package

Extract the deployment package archive into the designated application folder on the target host (e.g. C:\Applications\migration-dq-scanner).

Step 2 — Open PowerShell & Navigate to Project Root

Open a PowerShell session and move into the application directory:

cd C:\Applications\migration-dq-scanner
Step 3 — Verify Python Installation

Confirm that CPython 3.11+ is installed and accessible in the system PATH:

python --version

Expected output: Python 3.11.x (or 3.12.x / 3.13.x). Verify it is a 64-bit architecture.

Step 4 — Create Isolated Virtual Environment

Create the local virtual environment inside the application root directory:

python -m venv .venv

This generates the .venv folder containing isolated copies of the Python binaries and standard library.

Step 5 — Configure Execution Policy & Activate Environment

If PowerShell script execution is restricted on the host, permit script execution for the current process, then activate:

# Temporarily permit script execution for current PowerShell session
Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned -Force

# Activate the virtual environment
.\.venv\Scripts\Activate.ps1

For Windows Command Prompt (CMD), use:

.venv\Scripts\activate.bat

Verification: The shell prompt must immediately display the (.venv) prefix.

7. Dependency Installation

With the (.venv) environment activated, install the versions and dependency constraints specified by requirements.txt.

Online Installation (Host with Internet Access)

# Ensure pip is up to date
python -m pip install --upgrade pip

# Install project runtime dependencies
python -m pip install -r requirements.txt

Offline / Internal Package Installation

Where outbound package installation is restricted, dependencies can be supplied through an approved offline/internal package source:

  1. On an internet-connected staging machine with matching OS and Python version, pre-download all wheels: 
    pip download -r requirements.txt -d .\wheelhouse
  2. Copy the wheelhouse\ directory onto the target machine inside the project root.
  3. Install offline using the local wheel repository: 
    python -m pip install --no-index --find-links=.\wheelhouse -r requirements.txt

8. Application Configuration

Data Quality Scanner enforces a strict, two-tier configuration governance model:

🔒 Configuration Governance Rule

User Business Rules belong strictly in config/config.yaml.
Administrator Engine Parameters belong strictly in config/admin_config.yaml.
Crucial Syntax Notice: date_rules (accepted date formats and column keyword hints) resides in config/admin_config.yaml, NOT in config/config.yaml.

1. User Business Rules (config/config.yaml)

Reviewed and modified by migration specialists and data analysts. Deployment engineers should ensure this file contains default templates for the target project:

  • datasets: Defines profiles (e.g. Customer_Master, Orders) specifying mandatory_fields: and duplicate_keys:.
  • field_character_rules: Maps column names to standard character regex presets (alpha_numeric_only, email_format, numeric_only, etc.).
  • relationships: Defines explicit foreign-key linkages (parent_dataset, parent_key, child_dataset, child_key).

2. Administrator Parameters (config/admin_config.yaml)

Controlled exclusively by deployment engineers and application administrators:

Parameter Group Default Values Deployment Impact / Guidance
checks.enabled All 8 checks active Master toggle list. Do not disable checks unless explicitly requested by the migration project lead.
scoring.severity_weights Critical: 15.0
High: 8.0
Medium: 3.0
Low: 1.0		 Penalty points deducted per defect category. Controls readiness sensitivity.
scoring.readiness_thresholds Ready: 90
Minor Cleansing: 75
Needs Cleansing: 50		 Threshold bands defining the overall readiness status badge.
duplicate_rules.thresholds High: 5.0%
Medium: 1.0%		 Percentage of duplicate records triggering High vs Medium severity.
null_rules.thresholds High: 20.0%
Medium: 5.0%		 Percentage of missing values in a column triggering High vs Medium severity.
date_rules.accepted_formats 8 standard date formats List of strptime patterns (e.g. %Y-%m-%d, %m/%d/%Y). Add legacy source formats here.

9. Branding and Static Assets

The application provides clean, corporate header branding in both the GUI and exported HTML/Excel reports.

Branding Configuration Schema

Configured in config/admin_config.yaml under the branding: key:

branding:
  title: "Data Quality Scanner"
  description: "Pre-Migration Data Quality Assessment"
  logo:
    enabled: true
    file: "assets/branding/company_logo.png"

Deployment Procedures for Corporate Assets

  1. Copy the organization's official logo image into assets/branding/ (e.g. assets/branding/acme_logo.png).
  2. Supported image formats: .png, .jpg, .jpeg, .svg.
  3. Update config/admin_config.yaml to reference the relative path: 
    file: "assets/branding/acme_logo.png"

Sizing Architecture & Fallback Behavior

  • Fixed-Height Anchor: The application header bar maintains a fixed, stable height (64 px). The logo is anchored to the far right.
  • Aspect-Ratio Scaling: Images are dynamically scaled using strict KeepAspectRatio. A large image will never expand the header height or distort text.
  • Graceful Fallback: If the specified logo file is missing, corrupt, or has enabled: false, the application automatically displays clean text branding without throwing errors or crashing.

10. Database and Persistence Setup

Data Quality Scanner includes an embedded SQLite database engine to maintain a historical log of completed scans.

Default Database Location & Initialization

  • Default Path: data/scanner.db (relative to the project root).
  • Auto-Initialization: When the application performs a scan, db/connection.py checks if data/scanner.db exists. If missing, it automatically creates the data/ folder and executes db/schema.sql to create all required tables, indexes, and relationships.
  • Zero Manual DDL: Deployment engineers do not need to execute SQL scripts or install SQLite binaries; SQLite is embedded directly in Python's standard library.

Operational Database Settings

Setting Value Operational Purpose
Journal Mode WAL (Write-Ahead Logging) Provides crash resilience, concurrency, and high performance for concurrent reads.
Foreign Keys PRAGMA foreign_keys = ON; Enforces referential integrity across scan records and defect findings.
Row Factory sqlite3.Row Permits efficient dictionary-style column access during UI reloads.

Privacy Guarantee

🛡️ Data Privacy & Compliance Statement

The SQLite database stores execution metadata (timestamps, dataset names, file paths, row counts), overall scores, dimension metrics, issue summary counts, and specific defect coordinates (row numbers, column names, error types). Raw dataset records and proprietary data rows are NEVER saved into the database.

Disabling Persistence in Batch / CLI Mode

On automated pipelines where scan results must remain strictly ephemeral, persistence can be bypassed by passing either --no-db or --skip-db: 

python batch_runner.py samples/customers_clean_100pct.csv --no-db --excel

12. Batch / CLI Deployment & Execution

The headless batch runner provides automated data quality assessment without initializing Qt, making it ideal for scheduled jobs, headless build servers, and automated pipelines.

Command Syntax

python batch_runner.py [options] DATASET [DATASET ...]

Command-Line Arguments Reference

Option / Flag Type Default Description
DATASET... Positional Required One or more CSV or Excel (.xlsx/.xls) dataset paths.
--config, -c CONFIG String config/config.yaml Custom business rules configuration file path.
--profile, -p PROFILE String None Dataset profile name defined in configuration (e.g. Customer_Master).
--output, -o OUTPUT String reports Target directory for generated assessment reports.
--db DB String data/scanner.db Custom SQLite database path for scan persistence.
--no-db, --skip-db Flag False Disable persisting scan findings to SQLite.
--sheet SHEET String / Int 0 Worksheet name or 0-based index when analyzing Excel workbooks.
--html Flag False Generate standalone HTML assessment report.
--excel Flag False Generate multi-sheet Excel (.xlsx) assessment report.
--json Flag False Generate machine-readable JSON structured export.
--no-reports Flag False Disable file-based report export entirely.
--quiet, -q Flag False Suppress human-readable console progress and summary output.
--version, -v Flag — Display program version and exit.
-h, --help Flag — Display command-line help documentation and exit.

Process Exit Codes

Exit Code Status Technical Meaning
0 Success Scan executed and completed cleanly (regardless of data defect severity).
1 CLI Argument Error Invalid command-line syntax, unknown flag, or missing dataset parameter.
2 Data / Config Error Input file not found, unreadable file format, or invalid YAML syntax.
3 Runtime Error Unhandled runtime or engine exception encountered during execution.

16. Updating an Existing Deployment

When deploying a minor release, patch, or configuration update to an active installation, follow this safe sequence:

  1. Terminate Running Processes: Close the Data Quality Scanner GUI and ensure no active user sessions or automated batch_runner.py jobs are running.
  2. Create Pre-Update Backup: Archive the current working state: 
    # Create timestamped backup folder
mkdir ..\backups\pre-update-backup
Copy-Item -Recurse config, data, assets, reports ..\backups\pre-update-backup\
  3. Deploy Updated Application Code: Overwrite core application packages (core/, gui/, rules/, db/, reports/, main.py, batch_runner.py). Do not overwrite modified business rules in config/config.yaml. The repository's report-generation modules/templates under reports/ are application code and may be replaced as part of an application update. Generated .xlsx, .html, and .json deliverables must be preserved or archived separately and must not be treated as application source files.
  4. Check Dependency Changes: Compare the new requirements.txt against the existing installation. If dependencies changed: 
    .\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
  5. Database Schema Notice: The application does not contain an automated database migration engine. If an update introduces changes to db/schema.sql, existing databases must be patched manually or archived before allowing the application to re-initialize a fresh schema.
  6. Re-Run Smoke Test Suite: Execute tests DT-06, DT-10, and DT-13 to ensure complete operational integrity.

17. Backup / Restore Considerations

Establishing a disciplined backup regime ensures migration audit logs and custom business rules are never lost.

What Must Be Backed Up

Directory / File Type Recommended Frequency Operational Impact if Lost
config/config.yaml Business Configuration After every rule change High: Loss of custom dataset definitions, mandatory fields, and relationship linkages.
config/admin_config.yaml Admin Configuration After every parameter change High: Loss of custom severity weights, detection thresholds, and branding settings.
data/scanner.db SQLite Database Daily during active migrations Medium: Loss of historical scan audit log and dashboard historical reload ability.
assets/branding/ Static Assets After logo changes Low: Loss of corporate artwork (falls back to default header text).
reports/ (deliverables) Deliverable Output Weekly / Milestone sign-off Medium: Loss of historical generated audit deliverables (.xlsx, .html, .json), which must be archived separately and must not be treated as disposable application files.

Restoration Sequence

To restore a damaged or corrupted installation:

  1. Stop all running instances.
  2. Copy backed up config.yaml and admin_config.yaml into config/.
  3. Copy backed up scanner.db into data/.
  4. Copy backed up logo files into assets/branding/.
  5. Launch the GUI and verify scan history displays past entries cleanly.

18. Rollback / Redeployment

If an application update causes unforeseen runtime errors or fails smoke testing, perform an immediate emergency rollback:

⚠️ Version Compatibility Warning

Never blindly mix configuration files or SQLite databases from disparate major versions. Always restore the exact matching configuration snapshot taken prior to the update.

Emergency Rollback Steps

  1. Terminate Application: Close the Data Quality Scanner GUI and stop any scanner-specific Batch/CLI process before beginning rollback.
  2. Restore Application Files: Overwrite application modules with the pre-update release archive.
  3. Restore Database & Configs: Copy the pre-update scanner.db and YAML files from ..\backups\pre-update-backup\ back into their respective directories.
  4. Reactivate Virtual Environment: 
    .\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
  5. Validate Rollback: Execute smoke test DT-13 to prove that the restored version executes successfully.

19. Deployment Troubleshooting

Common technical issues encountered during target host setup, along with root causes and corrective actions:

Observed Failure Probable Root Cause Corrective Engineering Action
python : The term 'python' is not recognized Python is not installed, or installer option "Add python.exe to PATH" was unchecked. Reinstall Python 3.11+ (64-bit) ensuring "Add Python to environment variables" is selected.
Python was not found; run without arguments to install from Microsoft Store Windows "App execution aliases" intercepting the python command. Open Settings > Apps > Advanced app settings > App execution aliases and toggle OFF "App Installer" for python.exe and python3.exe.
File .venv\Scripts\Activate.ps1 cannot be loaded because running scripts is disabled PowerShell execution policy defaults to Restricted on Windows. Run Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned -Force in PowerShell before activating.
ModuleNotFoundError: No module named 'PySide6' Virtual environment is inactive, or dependencies were not installed into .venv. Ensure prompt shows (.venv), then run python -m pip install -r requirements.txt.
PermissionError: [Errno 13] Permission denied: 'data/scanner.db' Target user lacks write permissions in data/, or file is locked by an existing process. Grant full Modify permissions to the local user account on the application folder. Ensure no orphaned python processes have the file open.
ConfigError: YAML formatting error in config.yaml Tab characters or malformed indentation in YAML configuration. Open YAML file in VS Code or Notepad++; replace all tabs with 2 spaces; validate syntax with python -c "import yaml; yaml.safe_load(open('config/config.yaml'))".
database is locked (sqlite3.OperationalError) Concurrent write access conflict or zombie process holding WAL file lock. Terminate all Python processes. Check for scanner.db-wal and scanner.db-shm files; restart the application.
PermissionError: Permission denied writing to reports/...xlsx An existing report with the same filename is currently open in Microsoft Excel. Close Microsoft Excel on the target machine and retry report generation.
CLI terminates with exit code 2 Input dataset path was invalid, file is unreadable, or config syntax is corrupted. Verify that dataset files exist at the specified relative or absolute paths. Run without --quiet to review stderr logs.
CLI terminates with exit code 3 Unhandled runtime or engine exception occurred. Inspect console traceback output; check dataset for corrupted byte sequences or unsupported complex formatting.

20. Security, Permissions & Operational Considerations

Technical operational controls to ensure secure, compliant execution on corporate target workstations:

User & Administrator Permissions Model

Data Quality Scanner distinguishes normal user/operator permissions from administrative rights according to the principle of least privilege:

  • Normal Users / Operators:
    • Read access to application files and configuration required for execution.
    • Write access to data/ when SQLite persistence is enabled.
    • Write access to reports/ for report generation.
  • Administrators:
    • Additional authorized write access to config/ when changing administrative configuration (e.g., admin_config.yaml).
    • Authorized access to assets/branding/ when updating corporate branding.
  • Execution Privileges: Normal application execution is designed to run under a standard Windows user account; administrative rights should only be required for host-level installation or enterprise policy changes.

Data Governance & Confidentiality

  • In-Memory Processing: Source datasets are processed in application memory. Raw dataset rows are not stored in the SQLite scan-history database.
  • Network Independence: Normal execution does not require a remote application server or cloud service. Where outbound package installation is restricted, dependencies can be supplied through an approved offline/internal package source.
  • Report Access Controls: Generated reports may contain actual field values and should therefore be stored in access-controlled locations according to organizational policy.
